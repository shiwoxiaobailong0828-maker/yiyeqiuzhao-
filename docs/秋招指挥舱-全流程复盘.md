# 秋招指挥舱（一页秋招）· 全流程复盘

> 一个单文件 HTML 的秋招求职管理看板，从"能记东西的表格"长成"带 AI 助手和云同步的个人工作台"。
> 本文记录：它是什么、怎么设计、踩过哪些坑、每个坑具体怎么改、以及还能往哪走。

---

## 一、这是什么

### 1.1 一句话定位

**把整场秋招收进一个网页文件**：投递记录、进度管道、目标岗位池、Offer 对比、行动待办、简历版本，加一个能对话的 AI 助手。

### 1.2 形态与边界

| 维度 | 选择 | 原因 |
|---|---|---|
| 载体 | **单个 .html 文件**（约 3700 行 / 372KB，HTML+CSS+JS 全内联） | 双击即用、发群里就能用、不用装环境 |
| 依赖 | **零第三方依赖** | 无 CDN 断供、无版本冲突、离线可用 |
| 存储 | **localStorage** | 数据不出本机；换设备靠导出 JSON 或云同步 |
| 部署 | 静态托管（GitHub Pages / 任意静态空间） | 没有后端也能活 |
| 隐私 | 默认不联网、不埋点、不上传 | 求职数据（公司、薪资、面试）敏感 |

### 1.3 名字的由来

最初叫「秋招工作台」，后来改成「秋招指挥舱」——因为它的角色不是"记录表格"，而是"告诉你今天该干什么"的作战中枢。文件名保持 `一页秋招.html`，寓意"一页看完"。

## 二、产品全景

### 2.1 六个板块

| 板块 | 解决的问题 | 关键设计 |
|---|---|---|
| 投递岗位 | 投了哪些、卡在哪一步 | 七阶段管道（已投递→筛选中→AI面试→笔试→复试→终试→Offer），卡片底色随进度加深 |
| 投递进度 | 整体打得怎么样 | 漏斗图、进行中占比环图、近 30 天趋势、渠道回音率/复试率 |
| 筛选岗位 | 该投哪些 | P0–P3 优先级目标池，带截止倒计时，一键转投递 |
| Offer 对比 | 选哪个 | 自定义维度权重自动打分，得分可追溯到原始值 |
| 待办事项 | 今天做什么 | 优先级 + 时间窗，跨板块聚合 |
| 使用说明 | 怎么用 | 功能清单、AI 能力、文件格式、云端配置手册 |

### 2.2 几个"主动提示"机制

产品里最有价值的不是录入，而是**主动发现风险**：

- **凉投标记**：30 天未更新的投递自动标注，避免"以为还在流程里"
- **数据体检**：简历库空、目标池空、长期筛选中，聚合成一条行动提示
- **截止倒计时**：目标岗位截止日 ≤14 天进入"今天要处理"
- **重复投递提醒**：AI 录入时检测同公司同岗位

### 2.3 交互细节（容易被忽略但影响手感）

- iOS 分段导航 + 毛玻璃
- 卡片 hover 上浮 + 阴影加深
- 弹层底部上滑 / 淡入淡出
- 面板切换缓动（cubic-bezier），不是瞬切
- 全端响应式：≤560px 表格转卡片堆叠

## 三、架构与技术决策

### 3.1 为什么坚持单文件

**收益**：
- 零部署门槛（发文件即可）
- 零依赖风险（不会因为 CDN 挂了打不开）
- 完全离线
- 数据天然私有

**代价**（必须承认）：
- 没有模块化，代码靠注释分区
- 改动需全文搜索定位
- 测试只能靠外部脚本（无构建工具）
- 文件会越来越长（现在 3753 行 / 372KB）

**判断**：目标用户是"一个求职的学生"，不是团队协作项目。单文件的收益远大于代价，所以一直没拆。

### 3.2 单一事实源与副本规范

```
一页秋招.html          ← 唯一事实源，唯一进 Git 的 HTML
deploy-qiuzhao/index.html  ← 发布产物，由事实源拷贝（不进 Git）
archive/                ← 旧版留档（不进 Git）
```

规则：**只改事实源，单向拷到发布版，md5 校验一致**。
踩过的坑：早期有三个内容相同的副本（模板/分发/发布），改一个忘一个，最后变成"线上是旧版"。后来彻底删除重复，只留一个源。

### 3.3 数据模型（简化）

```js
S = {
  profile: {name, school, major, degree, target},
  apps: [{
    id, co, ti, nat, date, ch, url,
    stage, terminal,          // 阶段 or 终态（拒绝/放弃）
    offer: {...},             // Offer 待遇明细
    interviews: [{round, date, form, questions, review}],
    history: [{d, stage, note}],  // 时间线，自动记账
    upd, note
  }],
  mt: [...],      // 目标岗位池
  todos: [...],   // 待办
  resumes: [...], // 简历版本（附件存 Base64）
  rev, savedAt    // 版本号，云同步用
}
```

## 四、AI 助手设计（核心）

### 4.1 设计目标

不是"聊天机器人"，而是**会动手的助手**：能把你口述的话变成结构化记录，能看懂你的数据给建议，能联网查实时信息。

四类能力：
1. **结构化填表**（function calling 写数据）
2. **主动分析**（注入全局统计，发现风险）
3. **智能纠错**（重复检测、字段校验）
4. **面试辅导**（STAR、追问预判）

### 4.2 配置流程：四步向导（仿 Obsidian Copilot）

```
① 填写厂商/地址/Key → ② 测试连接（并拉取模型列表）→ ③ 多选模型 → ④ 保存启用
```

**为什么这么设计**：
- 早期是"一个表单填完点保存"，结果用户填完 DeepSeek 地址又切成千问，地址没变 → 调用失败还不知道为什么
- 现在是**强制顺序**：不测试通过不给选模型，不选模型不能保存
- 测试时先请求 `/models`（验证 Key + 拿真实可用模型），拿不到再用最小对话探测
- 模型列表自动过滤 embedding / tts / asr / rerank 等非对话模型

### 4.3 Function Calling 工具表

| 工具 | 作用 |
|---|---|
| `add_application` | 新增投递（带重复检测） |
| `add_interview` | 加面试记录（找不到公司则新建） |
| `set_offer` | 写 Offer 待遇，并自动把阶段改为 Offer |
| `add_target` | 加目标岗位 |
| `add_todo` | 加待办 |
| `set_profile` | 更新档案 |
| `list_data` | 查当前数据（给分析用） |
| `coach_interview` | 面试辅导（不写数据） |

**关键设计：写入前必须确认**
AI 解析出的每条记录先进入"待确认列表"，按类型分组（投递/面试/Offer/目标/待办），用户勾选后才落盘。这解决了"AI 理解错就写脏数据"的问题。

### 4.4 上下文注入

每次请求的 system prompt 会动态拼接：

```
【用户已记录的公司/岗位】...（让 AI 优先匹配已有记录，不新建重复公司）
【当前整体数据概况】投递 43 笔（进行中 26、Offer 2、拒绝 9、放弃 5）；凉投 6 笔；目标 12 个、待办 7 条
【用户正在查看的页面数据】...（面板级上下文）
【联网检索状态】...
```

这是"AI 看起来懂我"的关键——不是模型更聪明，而是**把该给的信息喂对了**。

### 4.5 输出格式：纯文本 + 表情

**问题**：模型默认输出 Markdown（`##` 标题、`**加粗**`、表格），在聊天泡泡里显示成"源码"，非常丑。

**双保险**：
1. 提示词明令禁止 Markdown，要求用 `•` 和 `1. 2. 3.`，允许少量表情
2. 前端 `aiPlainText()` 再洗一遍（去标题、去加粗、表格转行、代码块去围栏）

**教训**：只靠提示词不保险，模型会"忘记"；必须有代码兜底。

### 4.6 快捷指令

把 8 个高频任务做成模板，输入 `/简历` 自动展开成完整提示：

| 指令 | 干什么 |
|---|---|
| `/复盘` | 结论 + 分布 + 最该做的 3 件事 |
| `/简历` | 简历诊断（配合上传 docx/pdf） |
| `/匹配` | 贴 JD 给 0-100 分与缺口 |
| `/模拟面试` | AI 当面试官，一次一题，5 轮后评分 |
| `/周报` | 可复制的本周小结 |
| `/谈薪` | 原则 + 可直接发 HR 的话 + 反问应对 |
| `/打招呼` | Boss 开场白 3 版 |
| `/查` | 联网查招聘/薪资/笔试考点 |

历史里只显示 `/匹配` 这种短指令（存 `disp` 字段），不显示展开后的长文本。

### 4.7 稳定性：十个坑与改法

AI 模块是 bug 重灾区，逐条记录：

| # | 现象 | 根因 | 改法 |
|---|---|---|---|
| 1 | 点"停止"没反应 | 发送按钮在请求中被 `disabled` | 请求中保持可点，文案改"停止" |
| 2 | 刷新后 AI 回复消失 | 流式内容只渲染 DOM，没写历史 | 流式结束后把累计文本落入 `aiChat` |
| 3 | 隔天打开就报错 | 历史被截断产生孤儿 `tool` 消息（tool_calls 无配对） | `aiSanitizeChat` 剔除残缺；`aiSaveChat` 按 user 轮次对齐 |
| 4 | 写入 Offer 后在页面看不到 | `set_offer` 只写 `offer`，没改 `stage` | 写入时同时置 `stage="Offer"` |
| 5 | 失败后历史被污染 | 失败时已 push 的用户消息没回滚 | 记录 `baseLen`，失败时 `aiChat.length=baseLen` |
| 6 | 重新打开面板预览丢了 | 只渲染历史，没恢复待确认列表 | `aiRenderHistory` 里补 `aiRenderPending()` |
| 7 | 额度用完却显示成功 | 第二段请求非 200 时静默返回 | 非 200 抛错，统一走失败分支 |
| 8 | 文档导入失败后输入框被撑爆 | 失败没恢复 `aiPendingDoc` | 失败时恢复文档状态 |
| 9 | 回答被存两遍 | `msgSafe` 已入历史，`aiBotMsg` 又存一次 | 该分支传 `save=false` |
| 10 | 来源链接不显示 | 只查 `message.search_info` | 兼容顶层/choices[i]/message 三处；正文 URL 也转链接 |

**通用教训**：
- 流式 + 历史 + 工具调用三者混在一起时，**必须先定义"哪一份是真相"**（我们用 `aiChat` 为唯一真相，DOM 只是投影）
- 任何异步失败路径都要能回到"发送前"的状态

## 五、云同步设计（最难的部分）

### 5.1 先回答一个根本问题：为什么必须自带后端

纯前端文件没有服务器，**两个设备无法直接找到对方**。想让手机和电脑共享数据，必须有一个"中间人"。

三种选择：

| 方案 | 问题 |
|---|---|
| 用公共服务器（作者提供） | 别人的公司名、薪资、面试记录都过你的服务器 —— 隐私不可接受，也担不起责任 |
| 用第三方网盘 API | 要 OAuth、限额、还得处理文件冲突，体验更差 |
| **让用户自带后端** | 每人自己跑一个，数据只属于自己的机器 |

**结论**：提供"可运行的服务端代码 + 傻瓜部署教程"，而不是公共云。

### 5.2 两套服务端

| 文件 | 适合 | 代价 |
|---|---|---|
| `云同步服务/server.js` | 手机和电脑同一 Wi-Fi | 要装 Node.js；电脑关机就同步不了 |
| `云同步服务/cloudflare-worker.js` | 手机在外面用 4G | 要注册 Cloudflare（免费）；不用装软件 |

两者**协议完全一致**，前端不用区分。

### 5.3 接口契约

```
GET  地址?token=xxx                     → {ok, data, enc, device, rev, updatedAt}
GET  地址?token=xxx&action=ping         → {ok, server, time}
POST 地址?token=xxx                     → body 为信封（见下）
POST 地址?token=xxx&action=save-chunk   → {key, index, total, data(base64)}
POST 地址?token=xxx&action=save-merge   → {key, total}
```

**信封格式**（关键设计）：

```json
{
  "payload": { ...全量数据... } 或 {"enc":1,"v":2,"salt":"...","iv":"...","ct":"..."},
  "enc": 0,
  "device": {"id":"dev_ab12","name":"家里电脑"},
  "ts": 1793880000000
}
```

为什么用信封而不是直接发数据：
- 设备信息要跟数据一起走（才知道"最后修改来自手机"）
- 加密后 payload 变成密文，服务端不需要理解内容
- 分片上传时，分片的是整个信封，合并后结构完整

### 5.4 版本与冲突（这块改了三次才对）

**第一版**：客户端 `S.rev = Date.now()`，云端也存 `rev`。比较大小决定谁新。
→ **问题**：两端时钟不同（手机快 2 分钟），比较必然错。

**第二版**：上传成功后**采用服务器返回的 rev**，两端统一时钟。
→ 有改善，但仍用 `cloudRev > localRev + 500ms` 判断，写入密集时会漏判。

**第三版（最终）**：记录 `_lastSyncedRev`（上次同步成功时的版本号），
`cloudChanged = cloudRev !== _lastSyncedRev` —— **精确比对，不依赖时间容差**。

**冲突处理原则**（重要）：

```
云端没数据        → 上传本机
本机没数据        → 直接拉云端
云端版本变了      → 只提示"云端有更新"，绝不自动覆盖本机
用户点"查看差异"  → 列出云端多出 / 本机独有 → 合并 / 覆盖 / 保留 三选一
```

**为什么不自动合并**：自动合并会掩盖冲突。求职记录里"同一条被两台设备改成不同阶段"必须让人决定。

### 5.5 端到端加密

- 口令 → PBKDF2（20 万次 + 16 字节随机盐）→ AES-GCM 256 密钥
- 每次上传生成随机 IV
- 服务端只存 `{enc:1,v:2,salt,iv,ct}`，**看不到任何公司名和薪资**
- 兼容旧密文：`v` 字段缺失时走老的 SHA 摘要派生
- 密钥缓存在内存（`_kc`），避免每次重算

**踩的坑**：
1. **PBKDF2 的 hash 参数写成了不存在的算法名** → `deriveKey` 永不返回，加密直接卡死。这是审查别人提交时发现的最严重 bug。（改法：用运行时拼接算法名，避开文本处理事故）
2. **关页时的 `sendBeacon` 兜底用明文上传** → 开了加密也会被覆盖成明文。改法：加密开启时禁用该兜底。

### 5.6 体验补全

| 能力 | 价值 |
|---|---|
| 每 60 秒自动检查云端 | 长时间挂着也能收到另一端的更新 |
| 本地改动后 1 秒防抖上传 | 不用手动点保存 |
| 失败自动重试（3 次 + 后台退避） | 弱网下不丢数据 |
| 分片上传（>90KB） | 简历附件带 Base64，整包容易超限 |
| 同步日志（最近 15 条） | 出问题能回溯，不用猜 |
| 设备标识 | "最后修改来自：我的手机" |
| 状态可视化 | 上次同步时间 / 本机修改时间 / 是否有更新 |

## 六、踩坑总表（按类型归纳）

### 6.1 CSS 类

**① 样式顺序覆盖 —— 拖拽手柄永远看不见**
```css
@media (min-width:760px){ .ai-resize-b{display:block} }  /* 写在前面 */
.ai-resize-b{display:none; ...}                          /* 写在后面，赢了 */
```
同优先级下后写的覆盖前面的。**改法**：在样式表末尾再写一次媒体查询，或把基础规则放前面。
**教训**：媒体查询不是"更高优先级"，它只是普通规则。

**② 动画冻结导致测量全错**
无头浏览器截图时，`animation` 停在第 0 帧（`translateX(100%)`），元素整体偏移一个自身宽度，所有 `getBoundingClientRect` 都不对。
**改法**：测试时注入 `*{animation:none!important}`。

### 6.2 JS 类

**③ 定时器竞态 —— 点"云端同步"没反应**
```
0ms    关闭菜单，启动 200ms 后隐藏
120ms  打开云端配置面板
200ms  旧定时器到点，把新面板一起隐藏 ← 面板"闪一下没了"
```
**改法**：`openSheet()` 打开前 `clearTimeout` 待执行的关闭定时器，并清掉 `closing` 类。
**教训**：任何"关一个开另一个"的 UI，都要处理进行中的过渡状态。

**④ localStorage 配额静默失败**
聊天记录越存越多，`setItem` 抛异常，被 `catch` 吞掉 → 历史"莫名丢失"。
**改法**：保存前剥离大字段（`reasoning_content`），并**逐级缩容重试**（60→30→15→6→2 条）。

**⑤ 跨时钟比较**
两端 `Date.now()` 不同源，比较必然错。改法见 5.4。

**⑥ 文本处理事故**
环境把字面量算法名里的数字改写成了别的值（`SHA-256` → `SHA-256`），导致加密挂掉且很难发现。
**改法**：关键字符串用运行时拼接（`"SHA-"+[2,5,6].join("")`），并加单元测试验证。

### 6.3 测试类

**⑦ jsdom ≠ 真实浏览器**
- 拿不到真实布局（宽高为 0），拖拽计算全错
- 不跑 CSS 媒体查询，手柄显示状态判断不了
- 不做真实 localStorage 配额

**结论**：布局/拖拽/截图必须用真实 Chrome；逻辑用 jsdom；加密用 Node WebCrypto。

**⑧ 无头浏览器的虚拟时钟会把加密线程饿死**
PBKDF2 10 万次以上在 `--virtual-time-budget` 下永不返回。**这不是代码 bug**，是测试环境限制。验证方式：改用 Node 的 WebCrypto 跑同一份函数。

**⑨ Chrome headless 有最小窗口宽度**
`--window-size=390` 实际视口约 511px，模拟不了真机 375px。早期据此误判"移动端严重溢出"。

### 6.4 外部接手（Antigravity 版）的改动清单

项目中途交给另一个 AI 工具改过一轮（commit `758745d`），出于"这份文档要能复现"的考虑，把它到底改了什么记下来：

| 改动 | 作用 | 验证结果 |
|---|---|---|
| `safeUrl()` 协议白名单 | 链接只允许 `http/https`，挡掉 `javascript:` / `data:` | ✅ 实测被拦 |
| `validateImport()` | 导入 JSON 前校验字段类型，坏数据拒绝并提示 | ✅ 返回「字段 apps 必须是数组」 |
| `localDate()` 替代 `toISOString()` | 修复时区导致的日期偏移（东八区凌晨会差一天） | ✅ 2026-01-05 正确 |
| pdf.js 加 SRI `integrity` | 第三方脚本防篡改 | ✅ 加载带完整性校验 |
| `uid()` 改用 `getRandomValues` | 降低 ID 碰撞概率 | ✅ |
| PBKDF2 + 16 字节随机盐（v2） | 加密从"单次哈希"升级到"密钥派生"，抗暴力破解 | ⚠️ 见下 |
| 清理 `data-page-node-id` 属性 | 去掉另一个工具留下的调试属性 | ✅ 文件内无残留 |

**其中一处引入致命 bug**：`deriveKey({... hash:"SHA-256"})` —— 不存在的算法名，导致 `deriveKey` 永不返回、开加密后上传直接卡死。已修为运行时拼接（`"SHA-"+[2,5,6].join("")`）。
**教训**：外部工具改完必须逐行审关键路径，尤其是密码学与网络请求——它们出错往往不报错，只是"卡住"。

### 6.5 产品类

**⑩ 重复文件**
三个内容相同的副本（模板/分发/发布），改一个漏一个，线上长期是旧版。
**改法**：删到只剩一个事实源，Git 只跟踪一个 HTML。

**⑪ 文档与实现脱节**
早期文档写"三副本同步"，实际已经改成两副本，新人（包括未来的自己）会被误导。
**改法**：每次改架构顺手改文档，且文档放在仓库里一起版本化。

**⑫ 用户以为"点了就成功"**
测试时我在他电脑上跑了一个本地服务，他点了"上传云端"成功，误以为这是公共能力。
**教训**：涉及"是否需要额外资源"的功能，必须在 UI 上写清楚，且失败时给可操作的提示，不能只弹一个成功 toast。

## 八、安全与隐私

| 风险 | 处理 |
|---|---|
| XSS（用户输入的 URL / 备注） | 渲染统一走 `esc()`；链接走 `safeUrl()` 只允许 http/https |
| 恶意导入 JSON | `validateImport()` 校验字段类型，不合法直接拒绝并提示 |
| API Key 泄露 | 只存本机 localStorage，直连厂商，不经第三方 |
| 第三方脚本被篡改 | pdf.js 加载加 SRI（`integrity` + `crossorigin`） |
| 云端明文 | 可选端到端加密，服务端只见密文 |
| 云同步被陌生人读 | token 校验，不匹配返回 401 |

## 十二、写在最后

这个项目最值得记的三条：

1. **"能跑"和"能稳定跑"是两件事**。前者靠功能，后者靠对边界情况的处理——失败回滚、配额重试、时钟对齐、竞态清理。
2. **不要把判断交给机器**。AI 解析错了会写脏数据，所以写入前必须人确认；云端有新数据会覆盖，所以只提示不自动合并。
3. **隐私是设计出来的，不是承诺出来的**。没有公共服务器、密钥只在本机、可端到端加密——这些是架构决定的，不是文案写的。

> 最后一句：这个文件从 2300 行长到 3753 行，改了几十轮，真正花时间的不是写功能，而是**找出"为什么它有时候不工作"**。那些坑，才是这份文档最值钱的部分。
